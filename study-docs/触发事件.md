# GitHub Actions 触发事件速查

GitHub Actions 通过 workflow 顶层的 `on` 配置触发事件。事件可以来自 GitHub 仓库活动、定时计划、其他 workflow，或 GitHub 外部系统。

## 1. 通用配置规则

| 配置 | 说明 |
|---|---|
| `on: <event>` | 监听一个事件，例如 `on: push`。 |
| `types` | 限制事件的 activity type；未指定时通常使用该事件的默认类型或全部支持类型。 |
| `branches` / `branches-ignore` | 按分支过滤。 |
| `tags` / `tags-ignore` | 按标签过滤。 |
| `paths` / `paths-ignore` | 按变更文件路径过滤。分支过滤和路径过滤同时配置时，必须同时满足。 |
| `workflow_dispatch.inputs` | 为手动运行提供输入参数。 |
| `schedule.cron` | 使用 POSIX cron 定时运行，默认使用 UTC。 |
| `repository_dispatch.types` | 过滤外部 API 发送的自定义 `event_type`。 |

## 2. 仓库和项目管理事件

| 事件 | 触发时机 | 常用 activity type / 配置 | 简要说明 |
|---|---|---|---|
| `branch_protection_rule` | 分支保护规则变化 | `created`、`edited`、`deleted` | 分支保护规则被创建、编辑或删除。 |
| `create` | 创建分支或标签 | 无 | 创建 Git reference。一次批量创建超过 3 个标签时不会产生事件。 |
| `delete` | 删除分支或标签 | 无 | 删除 Git reference。删除超过 3 个标签时不会产生事件。 |
| `deployment` | 创建部署记录 | 无 | 仓库中创建 deployment。 |
| `deployment_status` | 部署状态变化 | 无 | 第三方系统提供部署状态；状态为 `inactive` 时不会触发。 |
| `fork` | 仓库被 Fork | 无 | 有人创建仓库 Fork。 |
| `gollum` | Wiki 页面变化 | 无 | Wiki 页面被创建或更新。 |
| `image_version` | 指定镜像产生新版本 | `names`、`versions` | 可按镜像名称和版本 glob 过滤。 |
| `label` | 仓库 Label 变化 | `created`、`edited`、`deleted` | Label 被创建、编辑或删除；Issue 添加 Label 使用 `issues` 的 `labeled`。 |
| `milestone` | Milestone 变化 | `created`、`closed`、`opened`、`edited`、`deleted` | Milestone 被创建、打开、编辑、关闭或删除。 |
| `page_build` | GitHub Pages 发布源发生 push | 无 | GitHub Pages 启用时触发。 |
| `public` | 仓库从私有变为公开 | 无 | 仓库可见性变为 public。 |
| `watch` | 仓库被 Star | `started` | 用户为仓库添加 Star。 |

## 3. Issue、Discussion 和 Pull Request 事件

| 事件 | 触发时机 | 常用 activity type | 简要说明 |
|---|---|---|---|
| `issues` | Issue 变化 | `opened`、`edited`、`deleted`、`transferred`、`pinned`、`unpinned`、`closed`、`reopened`、`assigned`、`unassigned`、`labeled`、`unlabeled`、`locked`、`unlocked`、`milestoned`、`demilestoned`、`typed`、`untyped`、`field_added`、`field_removed` | 监听 Issue 本身的生命周期和字段变化。 |
| `issue_comment` | Issue 或 PR 的普通评论变化 | `created`、`edited`、`deleted` | 同时覆盖 Issue 评论和 PR conversation 评论。 |
| `discussion` | Discussion 变化 | `created`、`edited`、`deleted`、`transferred`、`pinned`、`unpinned`、`labeled`、`unlabeled`、`locked`、`unlocked`、`category_changed`、`answered`、`unanswered` | 监听 Discussion 本身；评论使用 `discussion_comment`。 |
| `discussion_comment` | Discussion 评论变化 | `created`、`edited`、`deleted` | 监听 Discussion 的评论。 |
| `pull_request` | Pull Request 活动 | `assigned`、`unassigned`、`labeled`、`unlabeled`、`opened`、`edited`、`closed`、`reopened`、`synchronize`、`converted_to_draft`、`locked`、`unlocked`、`enqueued`、`dequeued`、`milestoned`、`demilestoned`、`ready_for_review`、`review_requested`、`review_request_removed`、`auto_merge_enabled`、`auto_merge_disabled` | 默认常见类型为 `opened`、`synchronize`、`reopened`。 |
| `pull_request_review` | PR Review 变化 | `submitted`、`edited`、`dismissed` | 可通过 `github.event.review.state == 'approved'` 判断审批通过。 |
| `pull_request_review_comment` | PR diff 行评论变化 | `created`、`edited`、`deleted` | 只处理代码 diff 上的 review comment。 |
| `pull_request_target` | 以目标仓库默认分支上下文处理 PR 活动 | 与 `pull_request` 相同 | 可处理 Fork PR 的标签或评论；不要直接运行不可信 PR 代码。 |
| `merge_group` | PR 加入 merge queue | `checks_requested` | 使用 merge queue 时，必需检查应同时监听该事件。 |

> `pull_request_comment` 不是独立事件。PR 普通评论使用 `issue_comment`，代码 diff 评论使用 `pull_request_review_comment`。

## 4. Checks、状态和 Release 事件

| 事件 | 触发时机 | 常用 activity type / 配置 | 简要说明 |
|---|---|---|---|
| `check_run` | 单个 Check Run 变化 | `created`、`rerequested`、`completed`、`requested_action` | 监听单项检查运行状态。由 GitHub Actions 创建的 check suite 不会递归触发该事件。 |
| `check_suite` | Check Suite 变化 | `completed` | 监听一组 Check Runs 的汇总完成。 |
| `status` | Commit status 变化 | 无；使用 `github.event.state` 判断 | 状态通常为 `error`、`failure`、`pending` 或 `success`。 |
| `release` | Release 变化 | `published`、`unpublished`、`created`、`edited`、`deleted`、`prereleased`、`released` | Draft Release 的部分类型不会触发；需要稳定版和预发布版时通常监听 `published`。 |
| `registry_package` | GitHub Packages 活动 | `published`、`updated` | 包发布或更新；多架构镜像可能触发多次。 |

### check_run 完整场景示例

**场景：CI 测试失败时，由另一个 workflow 发出通知。**

仓库中有两个 workflow 文件：

**`ci.yml`**（负责跑测试，产生 Check Run）

```yaml
name: CI

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: python -m pytest
```

**`notify.yml`**（监听 Check Run 完成，测试失败时报警）

```yaml
name: Notify on Failure

on:
  check_run:
    types: [completed]

jobs:
  report-failure:
    if: github.event.check_run.conclusion == 'failure'
    runs-on: ubuntu-latest
    steps:
      - name: Report failure
        run: echo "Check Run 执行失败"
```

执行流程：

```
1. 开发者 push 代码到 main 分支
2. GitHub 触发 ci.yml，创建名为 test 的 Check Run
   → Check Run status = in_progress
3. pytest 运行失败，test job 结束
   → Check Run status = completed，conclusion = failure
4. GitHub 发出 check_run.completed 事件
5. notify.yml 被触发
   → 判断 github.event.check_run.conclusion == 'failure' 成立
   → 执行 report-failure job
```

关键字段说明：

| 字段 | 含义 | 示例值 |
|---|---|---|
| `github.event.check_run.status` | 当前运行状态 | `in_progress`、`completed` |
| `github.event.check_run.conclusion` | 完成后的结论（仅 status=completed 时有值） | `success`、`failure`、`cancelled` |
| `github.event.check_run.name` | 触发事件的 Check Run 名称 | `test` |

> `types: [completed]` 表示"某个 Check Run 的 status 变为 completed"，此时再通过 `conclusion` 判断是成功还是失败。`notify.yml` 本身不是被"自己的 CI 完成"触发，而是被任何一个 Check Run 完成后触发。

## 5. Push、外部和 workflow 链式事件

| 事件 | 触发时机 | 常用 activity type / 配置 | 简要说明 |
|---|---|---|---|
| `push` | 推送 commit、分支或标签 | `branches`、`branches-ignore`、`tags`、`tags-ignore`、`paths`、`paths-ignore` | 最常用的代码变更触发器。一次推送超过 5,000 个分支或 3 个标签时可能不产生事件。 |
| `repository_dispatch` | GitHub 外部系统调用 API | 自定义 `event_type`，可传 `client_payload` | 用于外部系统启动 workflow；`client_payload` 可在 `github.event` 中读取。 |
| `workflow_run` | 另一个 workflow 被请求、运行或完成 | `requested`、`in_progress`、`completed`；`workflows`、`branches` | 可根据 `github.event.workflow_run.conclusion` 判断上游结果；最多链式触发 3 层。 |
| `workflow_call` | 被另一个 workflow 调用 | `inputs`、`secrets`、`outputs` | 用于 reusable workflow，本身不直接响应 push 等仓库事件。 |

## 6. 定时和手动事件

| 事件 | 触发时机 | 常用配置 | 简要说明 |
|---|---|---|---|
| `schedule` | 到达 cron 时间 | `cron`、可选 `timezone` | 运行在默认分支最新提交上；最短间隔 5 分钟，高负载时可能延迟。 |
| `workflow_dispatch` | 用户、GitHub CLI 或 API 手动运行 | `inputs`、`choice`、`boolean`、`environment`、`string` | 支持手动选择分支/标签和输入参数；最多 25 个顶层输入。 |

## 7. 常用 SHA 和 Ref

| 事件 | `GITHUB_SHA`（简化） | `GITHUB_REF`（简化） |
|---|---|---|
| `push` | 推送到 ref 的 tip commit | 被更新的分支或标签 |
| `pull_request` | PR merge branch 的最后 merge commit | `refs/pull/<number>/merge` |
| `pull_request_target` | 默认分支最新 commit | 默认分支 |
| `merge_group` | merge group 的 SHA | merge group ref |
| `deployment` / `deployment_status` | 要部署的 commit | 要部署的分支或标签；仅使用 SHA 时可能为空 |
| `release` | tagged release 的最后 commit | `refs/tags/<tag>` |
| `workflow_dispatch` | 指定分支或标签的最后 commit | 被手动运行的分支或标签 |
| `workflow_call` | 与调用方 workflow 相同 | 与调用方 workflow 相同 |
| 其他仓库管理事件 | 默认分支最新 commit | 默认分支 |

## 8. 触发器选择示例

| 需求 | 推荐事件 |
|---|---|
| 代码提交后执行 CI | `push` |
| PR 创建或更新时执行检查 | `pull_request` |
| Merge queue 中执行必需检查 | `merge_group` |
| PR 审批后执行任务 | `pull_request_review` + `if` 判断 review state |
| 发布 Release 后构建或部署 | `release`，通常使用 `types: [published]` |
| 每天定时执行维护 | `schedule` |
| 手动选择环境部署 | `workflow_dispatch` + `inputs` |
| 另一个 workflow 完成后继续 | `workflow_run` |
| 复用公共 workflow | `workflow_call` |
| 外部系统触发 | `repository_dispatch` |
| 镜像发布后执行动作 | `registry_package` |

## 9. 重要注意事项

- 许多事件只有在 workflow 文件已经存在于默认分支时才会触发。
- `schedule` 只运行默认分支上的 workflow，并且公共仓库连续 60 天无活动后可能被自动禁用。
- Fork PR 默认不会把普通 secrets 传给 runner；`GITHUB_TOKEN` 通常为只读权限。
- `pull_request_target` 和 `workflow_run` 具有更高的权限和 secrets 访问风险，不要直接运行不可信代码。
- 通过 `GITHUB_TOKEN` 触发的部分事件不会再次创建 workflow run，以避免递归触发。
- `branches` 与 `paths` 同时设置时，两个条件必须同时满足。
- `workflow_run` 触发的 workflow 可以访问上游 run 信息和 artifact，但下载 artifact 时应使用正确的 `run-id`。
