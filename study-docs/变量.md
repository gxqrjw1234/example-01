默认变量 https://docs.github.com/zh/actions/reference/workflows-and-actions/variables#default-environment-variables



总结为以下五个核心部分：


**1. 在单个工作流中定义环境变量 (`env`)**

* **应用作用域**：可以在工作流顶部（全局）、`job` 级别或具体 `step` 级别通过 `env` 关键字配置。
* **解析时机**：这些变量是在任务发送到 Runner 虚拟机后由具体的 Shell 解析的，因此需注意不同操作系统的 Shell 语法差异（如 Linux/Bash 使用 `$NAME`，Windows/PowerShell 使用 `$env:NAME`）。

**2. 跨工作流定义配置变量 (`vars`)**

* **多层级配置**：可以在 Organization（组织）、Repository（仓库）或 Environment（环境）三个层级创建变量。
* **访问机制**：通过 `vars` 上下文读取（例如 `${{ vars.MY_VAR }}`）。未设置的变量会默认返回空字符串。

**3. 使用上下文 (`contexts`) 访问变量与控制逻辑**

* **`env` 上下文 vs Runner 环境变量**：
* 在 `run` 内部命令中，可以直接使用 Shell 原生语法（如 `$MY_VAR`）或者 `${{ env.MY_VAR }}`。
* 在 GitHub Actions 引擎自身处理的部分（如 `if` 条件判断），**必须**使用上下文语法 `${{ env.MY_VAR }}`。



**4. 操作系统检测与跨平台适配**

* 可以利用内部默认变量 `RUNNER_OS` 或对应的上下文 `${{ runner.os }}` 判断 Runner 运行的操作系统类型（如 `Linux`、`Windows`、`macOS`），从而在不同平台执行对应的脚本或命令。

**5. 步骤与作业间传递数据**

* **同一 Job 内跨 Step 传递**：把新变量值写入 `GITHUB_ENV` 环境文件中，后续 Step 即可读取该变量。
* **不同 Job 间传递**：需将步骤生成的值定义为 `job output`，供后续其他 Job 引用。

### 作业之间传递信息（Job Outputs）

如果要把信息从一个 Job 传递给另一个 Job，做法不是直接共享环境变量，而是：

1. 先在某个 step 中把值写入 `GITHUB_OUTPUT`
2. 再在 job 级别通过 `jobs.<job_id>.outputs` 暴露出去
3. 下游 job 用 `needs` 建立依赖，并通过 `needs.<job_id>.outputs.<name>` 读取

示例：定义 job 输出

```yaml
jobs:
	job1:
		runs-on: ubuntu-latest
		outputs:
			output1: ${{ steps.step1.outputs.test }}
			output2: ${{ steps.step2.outputs.test }}
		steps:
			- id: step1
				run: echo "test=hello" >> "$GITHUB_OUTPUT"
			- id: step2
				run: echo "test=world" >> "$GITHUB_OUTPUT"
```

示例：下游 job 声明依赖

```yaml
jobs:
	job2:
		runs-on: ubuntu-latest
		needs: job1
```

示例：读取上游 job 的输出

```yaml
jobs:
	job2:
		runs-on: ubuntu-latest
		needs: job1
		steps:
			- env:
					OUTPUT1: ${{ needs.job1.outputs.output1 }}
					OUTPUT2: ${{ needs.job1.outputs.output2 }}
				run: echo "$OUTPUT1 $OUTPUT2"
```

可以把它理解成：

- `GITHUB_OUTPUT`：step 级输出
- `jobs.<job_id>.outputs`：把 step 输出提升成 job 输出
- `needs.<job_id>.outputs.xxx`：下游 job 读取上游结果

这也是 GitHub Actions 中替代 GitLab `artifacts:reports:dotenv` 传递简单字符串值的标准方式。

### 内置环境文件变量（Environment File Variables）

GitHub Actions 有一组特殊的内置变量，**它们的值是文件路径**，而不是直接的数据值。runner 在每个 step 启动前创建这些文件，并把路径写入对应变量。通过向这些路径追加内容来触发效果，而不是直接赋值。

| 变量 | 用途 | 写入方式 |
|---|---|---|
| `$GITHUB_STEP_SUMMARY` | 向 Job Summary 写 Markdown，显示在 Actions UI 中 | `echo "## title" >> "$GITHUB_STEP_SUMMARY"` |
| `$GITHUB_OUTPUT` | 向同 job 的下游 step 输出变量，也可提升为 job output | `echo "key=value" >> "$GITHUB_OUTPUT"` |
| `$GITHUB_ENV` | 设置后续 step 的环境变量 | `echo "KEY=value" >> "$GITHUB_ENV"` |
| `$GITHUB_PATH` | 向 `PATH` 追加目录，后续 step 立即生效 | `echo "/my/tool/bin" >> "$GITHUB_PATH"` |
| `$GITHUB_STATE` | 在 composite/js action 的 pre 和 post 阶段之间传递状态 | `echo "key=value" >> "$GITHUB_STATE"` |

**与普通环境变量的区别：**

- 普通内置变量（如 `$GITHUB_SHA`、`$GITHUB_REF`）的值**直接就是数据**，读取即用。
- 环境文件变量的值是**临时文件路径**，需要写文件来触发效果。这是 runner 与 workflow 之间通信的机制，不能用 `export` 或直接赋值替代。

```bash
# 错误写法：直接赋值无效
GITHUB_ENV="MY_VAR=hello"

# 正确写法：追加到文件
echo "MY_VAR=hello" >> "$GITHUB_ENV"
```

**注意**：始终用 `>>` 追加而不是 `>` 覆盖，同一个 step 可能多次写入同一个文件。
