# GitHub Actions 工作流命令速查

工作流命令通过特殊格式的 `echo` 或写入环境文件，让 step 与 runner 进行通信。

## 1. 命令格式

```
echo "::command parameter1=value1,parameter2=value2::message"
```

命令名称和参数名称不区分大小写。

## 2. 常用命令一览

| 命令 | 写法 | 效果 |
|---|---|---|
| `::debug::` | `echo "::debug::msg"` | 打印调试日志（需开启 `ACTIONS_STEP_DEBUG` secret） |
| `::notice::` | `echo "::notice file=x,line=1::msg"` | PR diff 上显示蓝色通知 |
| `::warning::` | `echo "::warning file=x,line=1::msg"` | PR diff 上显示黄色警告 |
| `::error::` | `echo "::error file=x,line=1::msg"` | PR diff 上显示红色错误 |
| `::group::` / `::endgroup::` | 包裹一段 `run` | 日志折叠分组 |
| `::add-mask::` | `echo "::add-mask::$SECRET"` | 后续日志中该值变为 `***` |
| `::stop-commands::` / `::{token}::` | 传入唯一 token | 暂停 / 恢复工作流命令解析 |
| `GITHUB_ENV` | `echo "K=V" >> $GITHUB_ENV` | 跨步骤共享环境变量 |
| `GITHUB_OUTPUT` | `echo "k=v" >> $GITHUB_OUTPUT` | 步骤输出，供 `steps.id.outputs.k` 引用 |
| `GITHUB_STEP_SUMMARY` | `echo "## md" >> $GITHUB_STEP_SUMMARY` | Actions 运行页面的摘要卡片 |
| `GITHUB_PATH` | `echo "/path" >> $GITHUB_PATH` | 向 `PATH` 追加目录 |
| `GITHUB_STATE` | `echo "k=v" >> $GITHUB_STATE` | pre/post 操作之间传递状态 |

注解参数（`notice` / `warning` / `error` 共用）：

| 参数 | 说明 |
|---|---|
| `file` | 关联的文件名 |
| `line` | 起始行号 |
| `endLine` | 结束行号 |
| `col` | 起始列号 |
| `endColumn` | 结束列号 |
| `title` | 自定义标题 |

注解命令参数示例：

```
echo "::warning file=app.js,line=1,col=5,endColumn=7,title=YOUR-TITLE::Missing semicolon"
        │        │           │      │     │            │               │
        │        └─ 参数区   │      │     │            │               └─ 消息正文
        │                    │      │     │            └─ 结束列号 = 7
        │                    │      │     └─ 起始列号 = 5
        │                    │      └─ 行号 = 第 1 行
        │                    └─ 关联文件 = app.js
        └─ 命令名 = warning
```

效果：在 PR diff 页面的 `app.js` 第 1 行第 5-7 列显示标题为 `YOUR-TITLE`、内容为 `Missing semicolon` 的黄色警告注释。

三种注解命令的区别：

| 命令 | 颜色 | 是否导致 job 失败 |
|---|---|---|
| `::notice::` | 蓝色 | 否 |
| `::warning::` | 黄色 | 否 |
| `::error::` | 红色 | 否（需配合 `exit 1`） |

## 3. 完整示例

以下 job 将常用命令串联在一起：

```yaml
jobs:
  demo:
    runs-on: ubuntu-latest
    steps:
      # 1. 调试消息（需要 ACTIONS_STEP_DEBUG secret = true）
      - name: Debug log
        run: echo "::debug::开始构建"

      # 2. 设置环境变量（供后续步骤使用）
      - name: Set env
        run: echo "APP_VERSION=1.0.0" >> "$GITHUB_ENV"

      # 3. 设置输出参数（供后续步骤或 job 引用）
      - name: Set output
        id: meta
        run: echo "build_time=$(date +'%Y-%m-%d')" >> "$GITHUB_OUTPUT"

      # 4. 分组日志
      - name: Build
        run: |
          echo "::group::安装依赖"
          pip install -r requirements.txt
          echo "::endgroup::"
          echo "::group::执行构建"
          python build.py
          echo "::endgroup::"

      # 5. 屏蔽敏感值（不会出现在日志里）
      - name: Mask secret
        run: |
          TOKEN=$(curl -s https://example.com/get-token)
          echo "::add-mask::$TOKEN"
          echo "token=$TOKEN" >> "$GITHUB_OUTPUT"

      # 6. 写作业摘要（显示在 Actions 运行页面）
      - name: Summary
        run: |
          echo "## 构建结果" >> "$GITHUB_STEP_SUMMARY"
          echo "- 版本：$APP_VERSION" >> "$GITHUB_STEP_SUMMARY"
          echo "- 时间：${{ steps.meta.outputs.build_time }}" >> "$GITHUB_STEP_SUMMARY"

      # 7. 带文件位置的警告/错误注释（会显示在 PR 的文件 diff 上）
      - name: Lint check
        run: |
          echo "::warning file=src/app.py,line=10::变量未使用"
          echo "::error file=src/app.py,line=25,title=语法错误::缺少冒号"
```

## 4. 环境变量 vs 输出参数

| 对比点 | `GITHUB_ENV` | `GITHUB_OUTPUT` |
|---|---|---|
| 引用方式 | `$MY_VAR`（shell 直接使用） | `${{ steps.id.outputs.key }}` |
| 作用范围 | 同 job 内所有后续步骤 | 同 job 内后续步骤 + 其他 job（通过 `needs`） |
| 适用场景 | 构建版本号、时间戳等元数据 | 跨步骤或跨 job 传递计算结果 |

## 5. 多行值写法

```yaml
- name: Set multiline env
  run: |
    {
      echo 'JSON_DATA<<EOF'
      curl https://api.example.com/data
      echo EOF
    } >> "$GITHUB_ENV"
```

多行输出参数同理，将 `$GITHUB_ENV` 替换为 `$GITHUB_OUTPUT`。

## 6. 注意事项

- `::add-mask::` 必须在该值被打印到日志之前执行。
- 不能覆盖 `GITHUB_*` 和 `RUNNER_*` 开头的默认环境变量。
- `GITHUB_STATE` 仅在 Action 的 `pre` / `post` 阶段可用，普通 workflow step 不适用。
- 作业摘要每个步骤最大 1 MiB，每个 job 最多显示 20 个步骤的摘要。
- 通过 `GITHUB_TOKEN` 触发的事件不会递归触发新的 workflow run。
