# GitHub Actions `permissions` 权限详解

本文详细说明 GitHub Actions 工作流中的 `permissions` 配置、`GITHUB_TOKEN` 的关系、常见权限范围、最小权限设计、Fork/Dependabot 限制，以及本仓库 CI/CD 工作流中的实际用法。

## 1. 先记住三个结论

1. `permissions` 控制的是工作流使用的 `GITHUB_TOKEN` 可以调用哪些 GitHub API，不是 runner 操作系统的权限。
2. 权限应当按 job 划分：测试 job 通常只需要 `contents: read`，发布或删除 job 才增加对应的 `write` 权限。
3. 只要写出一个具体权限，其他未列出的权限就会被设为 `none`。因此 job 级别的权限块中要把该 job 需要的全部权限写完整。

推荐的默认起点是：

```yaml
permissions:
	contents: read
```

然后在确实需要写入 GitHub 的 job 上单独增加权限，例如：

```yaml
jobs:
	publish:
		permissions:
			contents: read
			packages: write
```

---

## 2. `permissions` 到底控制什么

GitHub Actions 每次运行时都会为工作流提供一个短期有效的 `GITHUB_TOKEN`。这个 token 通常以以下形式使用：

```yaml
env:
	GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

也可以直接传给 Action：

```yaml
- name: Call GitHub API
	uses: actions/github-script@v7
	with:
		github-token: ${{ secrets.GITHUB_TOKEN }}
		script: |
			const { data } = await github.rest.repos.get({
				owner: context.repo.owner,
				repo: context.repo.repo,
			});
			console.log(data.full_name);
```

`GITHUB_TOKEN` 可以理解为 GitHub 为当前仓库和当前工作流临时发放的安装访问 token。它具有以下特点：

- 由 GitHub 自动生成，不需要手动创建 PAT。
- 一般只作用于当前仓库或当前工作流可访问的资源。
- 生命周期短，job 结束或达到有效期后失效。
- 权限由企业、组织、仓库设置以及 YAML 中的 `permissions` 共同决定。
- Action 即使没有显式接收 token，也可能通过 `github.token` 上下文访问它，因此不能只依赖“没有写 `token` 参数”来保护 token。
- token 的 GitHub API 权限不等于 runner 的操作系统权限，也不等于云平台权限。

`permissions` 的作用是把 token 的能力限制为若干个独立的权限范围，例如：

```yaml
permissions:
	contents: read
	issues: write
	packages: write
```

上面的配置表示：

- 可以读取仓库内容。
- 可以创建或修改 Issue 相关数据。
- 可以发布或删除满足 GitHub 规则的 Package。
- 其他未列出的权限为 `none`。

### 2.1 `permissions` 不控制哪些内容

以下能力不由 `permissions` 直接授予：

| 内容 | 由什么控制 | 说明 |
|---|---|---|
| 云平台资源 | Azure/AWS/GCP 的角色、OIDC 信任策略或云端密钥 | `id-token: write` 只能让工作流获取 OIDC token，不会自动获得 Azure、AWS 或 GCP 资源权限 |
| 仓库 Secrets | 仓库、组织和 Environment 的 Secret 配置 | `contents: write` 不等于可以读取所有 Secrets；但一个能执行任意脚本且可访问 Secrets 的 job 仍可能泄露它们 |
| 仓库 Variables | 仓库、组织和 Environment 的 Variables 配置 | Variables 通常用于非敏感配置，不是 API 授权范围 |
| runner 的文件和进程 | runner 操作系统权限、容器配置和 self-hosted runner 配置 | `permissions: {}` 也不能阻止脚本读写 runner 本地可访问的文件 |
| 第三方 PAT 或 GitHub App token | 该 PAT 或 GitHub App 的自身权限 | 如果 Action 使用 `secrets.MY_PAT`，实际 API 权限由 PAT 决定，而不是由 `GITHUB_TOKEN` 的 `permissions` 决定 |
| Environment 审批 | Environment 的 Required reviewers、分支规则和保护规则 | `deployments: write` 不会绕过人工审批 |

## 3. 语法和权限级别

### 3.1 工作流级别

工作流级别的 `permissions` 写在顶层，作用于该工作流的所有 job：

```yaml
name: CI

on:
	push:

permissions:
	contents: read

jobs:
	test:
		runs-on: ubuntu-latest
		steps:
			- uses: actions/checkout@v4
			- run: python -m unittest
```

这适合给所有 job 设置共同的只读基线。

### 3.2 job 级别

job 级别的 `permissions` 写在具体 job 下，只影响该 job：

```yaml
jobs:
	test:
		runs-on: ubuntu-latest
		permissions:
			contents: read
		steps:
			- uses: actions/checkout@v4

	publish:
		runs-on: ubuntu-latest
		permissions:
			contents: read
			packages: write
		steps:
			- uses: actions/checkout@v4
			- run: echo "publish package"
```

这是最推荐的写法：测试 job 和发布 job 不共享不必要的写权限。

### 3.3 `read`、`write` 和 `none`

| 值 | 含义 |
|---|---|
| `read` | 允许读取对应资源；不能进行写入、删除或修改操作 |
| `write` | 允许写入对应资源，通常也包含 `read` 能力 |
| `none` | 禁止使用该权限范围 |

`write` 包含 `read`，所以通常不需要同时写：

```yaml
packages: read
packages: write
```

上面的重复配置没有意义，最终只保留：

```yaml
packages: write
```

### 3.4 使用空权限集合

如果某个 job 完全不需要 GitHub API，可以显式关闭所有 `GITHUB_TOKEN` 权限：

```yaml
permissions: {}
```

这不会关闭 job，也不会阻止脚本执行，只是让 `GITHUB_TOKEN` 没有仓库 API 权限。

### 3.5 `read-all` 和 `write-all`

GitHub 支持以下简写：

```yaml
permissions: read-all
```

```yaml
permissions: write-all
```

还可以使用：

```yaml
permissions: {}
```

学习或临时排错时可以使用 `read-all`，但生产工作流不建议使用 `write-all`。它会让一个被恶意修改或被攻破的 Action 获得远超实际需要的写权限。

### 3.6 省略的权限会变成 `none`

下面的配置只授予 `packages: write`：

```yaml
permissions:
	packages: write
```

它不会自动保留顶层的 `contents: read`。如果这个 job 还需要 checkout，就必须写成：

```yaml
permissions:
	contents: read
	packages: write
```

可以把 job 级权限理解为该 job 的完整有效权限清单，而不是普通 YAML map 的简单“增量追加”。

### 3.7 特殊权限值

- `id-token` 只支持 `write` 或 `none`。OIDC 获取 token 需要 `id-token: write`。
- `vulnerability-alerts` 只支持 `read` 或 `none`，用于读取 Dependabot alerts，不支持 `write`。
- 其他权限通常支持 `read`、`write` 和 `none`，具体仍以 GitHub 当前工作流语法为准。

### 3.8 不写 `permissions` 时的默认行为

不写 `permissions` **不等于自动使用 `write-all`**。此时 GitHub 会使用企业、组织或仓库设置中的默认 `GITHUB_TOKEN` 权限。

可以按以下情况理解：

| 配置情况 | 有效权限来源 |
|---|---|
| 工作流和 job 都不写 `permissions` | 企业、组织或仓库的默认权限 |
| 只在工作流顶层写 `permissions` | 所有 job 默认使用工作流级权限 |
| 某个 job 自己写 `permissions` | 该 job 使用自己的权限；未列出的 scope 为 `none` |
| 工作流顶层和 job 都写 | 该 job 使用 job 级配置，其他 job 使用工作流级配置 |

例如，下面的工作流没有声明 `permissions`：

```yaml
name: Example

on: push

jobs:
	test:
		runs-on: ubuntu-latest
		steps:
			- uses: actions/checkout@v4
```

`test` 的权限不是由这段 YAML 固定决定的，而是取决于仓库的 **Settings → Actions → General → Workflow permissions**，以及组织和企业策略：

- 如果默认设置是 **Read repository contents permission**，通常只有 `contents: read` 等受限读取能力。
- 如果默认设置是 **Read and write permissions**，默认权限可能比较宽，包含多个 scope 的写能力。
- 即使默认设置允许写入，也不应把它简单理解为在任何事件下都等同于 `permissions: write-all`；组织策略、Fork Pull Request、Dependabot 和其他 GitHub 安全规则仍可能进一步限制权限。

如果工作流顶层显式写了：

```yaml
permissions:
	contents: read
```

那么所有未单独配置 job 级权限的 job 都使用 `contents: read`，而不是继续使用仓库默认的广泛权限。

如果只有某个 job 显式写了权限：

```yaml
jobs:
	publish:
		permissions:
			contents: read
			packages: write
		runs-on: ubuntu-latest
		steps:
			- uses: actions/checkout@v4

	test:
		runs-on: ubuntu-latest
		steps:
			- uses: actions/checkout@v4
```

这里：

- `publish` 使用明确声明的 `contents: read` 和 `packages: write`。
- `test` 没有 job 级配置，因此继续使用工作流顶层配置；如果顶层也没有配置，则使用仓库、组织或企业默认值。

生产工作流不建议依赖未声明的默认权限。推荐显式写出只读基线：

```yaml
permissions:
	contents: read
```

并在确实需要写入的 job 中单独增加权限：

```yaml
jobs:
	publish:
		permissions:
			contents: read
			packages: write
```

因此，判断“不写 `permissions` 是否安全”时，不能只看工作流文件，还要同时检查仓库、组织和企业的 **Workflow permissions** 设置，以及当前工作流的触发事件。

## 4. 权限是如何计算出来的

一个 job 的最终 `GITHUB_TOKEN` 权限通常按以下顺序确定：

1. 企业级默认设置。
2. 组织级默认设置。
3. 仓库级默认设置。
4. 工作流顶层的 `permissions`。
5. job 级别的 `permissions`。
6. Fork Pull Request、Dependabot 等事件的安全降级规则。
7. Environment、仓库设置、组织策略等额外限制。

可以用下面的心智模型理解：

```text
企业/组织/仓库默认值
				↓
工作流 permissions
				↓
job permissions
				↓
Fork/Dependabot/策略限制
				↓
最终 GITHUB_TOKEN 权限
```

YAML 只能在上层设置允许的范围内配置权限，不能突破组织或仓库策略授予更高权限。组织管理员还可以限制工作流是否允许使用写权限。

### 4.1 仓库设置中的默认权限

在仓库的 **Settings → Actions → General → Workflow permissions** 中，通常可以选择：

- 允许 `GITHUB_TOKEN` 读取仓库内容。
- 允许 `GITHUB_TOKEN` 读取和写入仓库内容。

生产仓库通常应选择只读默认值，再在特定 job 中显式增加权限。这样即使新增了一个 job，也不会意外继承全仓库写权限。

组织或企业设置可能进一步限制仓库的 Actions 权限，实际结果以 GitHub 运行日志和仓库设置为准。

### 4.2 job 级权限的覆盖规则

例如顶层写了：

```yaml
permissions:
	contents: read
```

但某个 job 写成：

```yaml
jobs:
	publish:
		permissions:
			packages: write
```

那么 `publish` job 不应假设仍然拥有 `contents: read`。如果它要执行 `actions/checkout`，应明确写出：

```yaml
jobs:
	publish:
		permissions:
			contents: read
			packages: write
```

### 4.3 Fork Pull Request

来自 Fork 的 `pull_request` 工作流需要特别谨慎：

- 通常不能向 Fork Pull Request 提供写权限。
- `write` 权限通常会被降级为 `read`。
- Fork Pull Request 通常不能访问上游仓库 Secrets。
- 来自不可信分支的代码不应在拥有写权限或生产 Secrets 的 job 中执行。

不要为了让 Fork PR 通过而随意使用 `pull_request_target`。该事件在目标仓库上下文中运行，可能拥有更高权限和 Secrets；如果同时 checkout 并执行未经审查的 PR 代码，攻击者可能借此取得仓库权限。

更安全的做法是把流程分成两部分：

1. 使用普通 `pull_request` 运行不需要 Secrets 的构建和测试。
2. 只有在可信分支或经过审核的流程中，才运行需要写权限的发布、评论或部署 job。

### 4.4 Dependabot

由 Dependabot Pull Request 触发的工作流通常按 Fork 工作流处理：

- `GITHUB_TOKEN` 以只读方式运行。
- 工作流不能访问 Secrets。
- 需要写入仓库或访问私有服务时，应使用经过审核的后续流程，而不是直接给 Dependabot PR 写权限。

## 5. 可用权限范围参考

下面的表格按 GitHub Actions 工作流语法中常用的权限范围整理。某些权限与 GitHub 的具体功能、套餐或仓库配置有关。

| 权限范围 | 主要用途 | 常见 `write` 操作 |
|---|---|---|
| `actions` | 读取和管理 GitHub Actions 工作流、运行记录和相关数据 | 取消、重新运行或管理工作流运行；跨工作流读取通常使用 `read` |
| `artifact-metadata` | 构建产物的元数据 | 为构建产物创建或修改元数据记录；仅在使用相关功能时配置 |
| `attestations` | Artifact attestations、构建来源证明 | 为构建产物生成 provenance/attestation |
| `checks` | Check runs 和 Check suites | 创建或更新检查结果 |
| `code-quality` | GitHub Code Quality 相关数据 | 上传代码质量或覆盖率数据 |
| `contents` | 仓库代码、提交、分支、标签及部分仓库内容 | 推送代码、创建 Release、修改仓库内容 |
| `deployments` | Deployment 和 Deployment status 记录 | 创建部署记录、更新部署状态 |
| `discussions` | GitHub Discussions | 创建、编辑、关闭或删除 Discussion |
| `id-token` | OIDC 身份令牌 | 只能用 `write` 获取 OIDC token；不直接授予云资源权限 |
| `issues` | Issues 及 Issue comments | 创建、编辑、关闭 Issue 或添加评论 |
| `packages` | GitHub Packages、GHCR | 发布、删除或管理 Package；读取镜像通常使用 `read` |
| `pages` | GitHub Pages | 请求 Pages 构建或部署 |
| `pull-requests` | Pull Request 数据 | 添加标签、修改 PR 元数据或执行其他 PR 写操作 |
| `security-events` | Code scanning alerts | 上传或更新代码扫描结果；不等于 Secret scanning 权限 |
| `statuses` | Commit statuses | 创建或更新 commit status |
| `vulnerability-alerts` | Dependabot alerts | 只能读取 Dependabot alerts，不支持写入 |

### 5.1 `contents`

`contents` 是最常见的权限范围：

```yaml
permissions:
	contents: read
```

常见用途：

- `actions/checkout` 读取仓库代码。
- 读取提交、分支、标签和文件。
- 让脚本访问仓库内容 API。

`contents: write` 的能力较大，可能允许工作流推送代码、修改标签或创建 Release。除非确实需要，否则不要给测试 job 使用。

### 5.2 `packages`

GHCR 发布通常需要：

```yaml
permissions:
	contents: read
	packages: write
```

其中：

- `contents: read`：读取仓库内容以及执行 checkout。
- `packages: write`：用于推送容器镜像。
- `GITHUB_TOKEN` 作为 Docker Registry 密码使用。

示例：

```yaml
- name: Log in to GHCR
	uses: docker/login-action@v3
	with:
		registry: ghcr.io
		username: ${{ github.actor }}
		password: ${{ secrets.GITHUB_TOKEN }}
```

`packages: write` 也应视为敏感写权限。发布和删除最好拆到独立 job，并通过分支、标签或 Environment 保护条件限制触发范围。

### 5.3 `actions`

`actions` 面向 GitHub Actions 的管理 API，例如读取工作流运行、读取其他运行的信息、取消或重新运行工作流。

跨工作流读取运行或下载指定运行中的 Artifact 时，常见配置是：

```yaml
permissions:
	contents: read
	actions: read
```

而取消、重新运行或通过 API 调度其他工作流等管理操作，通常需要更高的 `actions: write`。普通的同一工作流 Artifact 上传/下载不要因为使用了 `upload-artifact` 或 `download-artifact` 就盲目增加 `actions: write`，应以 Action 文档和实际 API 调用为准。

### 5.4 `deployments`

需要创建 Deployment 记录或更新 Deployment status 时使用：

```yaml
permissions:
	contents: read
	deployments: write
```

它只控制 GitHub Deployment API，不代表已经获得云平台的部署权限。真正访问 Azure App Service、Kubernetes、AWS 等资源，还需要云端身份认证和对应的云端 RBAC。

### 5.5 `issues` 和 `pull-requests`

自动创建 Issue 或发表评论：

```yaml
permissions:
	issues: write
```

自动给 Pull Request 添加标签或修改 PR 数据：

```yaml
permissions:
	pull-requests: write
```

具体 REST 或 GraphQL endpoint 可能使用不同的权限范围。遇到 403 时，应以该 endpoint 的官方文档为准，不要直接改成 `write-all`。

### 5.6 `checks` 和 `statuses`

二者都可以在提交页面显示自动化结果，但对象不同：

- `checks` 面向 Check run 和 Check suite，信息通常更丰富。
- `statuses` 面向传统 commit status。

示例：

```yaml
permissions:
	contents: read
	checks: write
	statuses: write
```

只使用其中一种能力时，只授予对应权限。

### 5.7 `security-events`

CodeQL 或其他 Code scanning 工具上传扫描结果时，常见配置是：

```yaml
permissions:
	actions: read
	contents: read
	security-events: write
```

`security-events` 不代表可以读取所有安全数据：

- Code scanning 使用 `security-events`。
- Dependabot alerts 使用 `vulnerability-alerts: read`。
- Secret scanning alerts 通常需要 GitHub App 或其他专用凭据。

### 5.8 `id-token`

OIDC 工作流通常需要：

```yaml
permissions:
	contents: read
	id-token: write
```

`id-token: write` 的含义是允许工作流向 GitHub 请求一个 OIDC 身份令牌。它不会自动授予 Azure、AWS 或 GCP 权限；云平台仍需配置：

- 可信的 GitHub 仓库、分支、标签或 Environment 条件。
- 对应的云端角色或服务主体权限。
- 受限制的 audience 和 subject 条件。

OIDC 的优势是使用短期令牌，避免把长期云密钥保存为 GitHub Secret。

## 6. 常用配置模板

### 6.1 只读 CI

适用于 checkout、编译、单元测试、静态检查：

```yaml
permissions:
	contents: read
```

如果 job 不需要访问 GitHub API，也可以使用：

```yaml
permissions: {}
```

### 6.2 发布 GHCR 镜像

```yaml
jobs:
	build-image:
		runs-on: ubuntu-latest
		permissions:
			contents: read
			packages: write
		steps:
			- uses: actions/checkout@v4
			- uses: docker/login-action@v3
				with:
					registry: ghcr.io
					username: ${{ github.actor }}
					password: ${{ secrets.GITHUB_TOKEN }}
			- uses: docker/build-push-action@v6
				with:
					push: true
					tags: ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
```

### 6.3 从其他 CI 运行读取 Artifact

```yaml
jobs:
	deploy:
		runs-on: ubuntu-latest
		permissions:
			contents: read
			actions: read
		steps:
			- name: Download artifact from a specific run
				uses: actions/download-artifact@v4
				with:
					name: image-meta-${{ github.sha }}
					run-id: ${{ inputs.ci-run-id }}
					github-token: ${{ secrets.GITHUB_TOKEN }}
```

这里只增加读取权限，不应为了下载 Artifact 而增加 `actions: write`。

### 6.4 创建 Deployment 记录

```yaml
jobs:
	deploy:
		runs-on: ubuntu-latest
		environment: staging
		permissions:
			contents: read
			deployments: write
		steps:
			- run: echo "deploy to staging"
```

Environment 的审批规则仍然有效。若部署命令还需要访问云平台，应另外配置 OIDC 或云端凭据。

### 6.5 Azure/AWS/GCP OIDC

```yaml
jobs:
	cloud-deploy:
		runs-on: ubuntu-latest
		permissions:
			contents: read
			id-token: write
		steps:
			- uses: actions/checkout@v4
			- name: Authenticate to cloud provider
				uses: example/cloud-login-action@v1
			- run: ./deploy.sh
```

示例中的 `example/cloud-login-action` 只是占位符。云端信任策略必须限制到具体仓库、分支、Environment 和 audience。

### 6.6 自动评论 Issue

```yaml
jobs:
	comment:
		runs-on: ubuntu-latest
		permissions:
			issues: write
		steps:
			- name: Comment on issue
				env:
					GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
				run: gh issue comment "${{ github.event.issue.number }}" --body "处理完成"
```

### 6.7 Code scanning

```yaml
jobs:
	codeql:
		runs-on: ubuntu-latest
		permissions:
			actions: read
			contents: read
			security-events: write
		steps:
			- run: echo "run code scanning"
```

实际使用的扫描 Action 可能需要额外权限，应以该 Action 的官方文档为准。

### 6.8 完全关闭 token API 权限

```yaml
jobs:
	local-test:
		runs-on: ubuntu-latest
		permissions: {}
		steps:
			- run: python -m unittest
```

如果这个 job 后续需要 checkout、写摘要之外的 GitHub API 操作，再按实际需要增加权限。

## 7. 本仓库中的权限设计

本仓库目前采用“工作流只读基线 + 特定 job 增加写权限”的方式。

### 7.1 CI 工作流

在 [ci.yml](../.github/workflows/ci.yml) 中，工作流级别设置了：

```yaml
permissions:
	contents: read
```

这适合 `lint`、`test` 和 `build`，因为这些 job 主要需要读取代码并生成本地构建结果。

Docker 发布 job 单独设置：

```yaml
permissions:
	contents: read
	packages: write
```

原因如下：

- `contents: read`：读取仓库内容以及执行 checkout。
- `packages: write`：向 GHCR 推送 `linux/amd64` 镜像。
- 其他 job 不需要 `packages: write`，因此不会继承这个高风险写权限。

CI 中的普通构建 Artifact 与 GHCR Package 是两个不同概念：

- `upload-artifact` 上传的是 Actions 运行产物。
- GHCR 推送的是 Package/Container image。
- 不能因为要上传构建 Artifact 就把 `packages: write` 加到所有 job。

### 7.2 CD 工作流

在 [cd.yml](../.github/workflows/cd.yml) 中使用：

```yaml
permissions:
	contents: read
	actions: read
	deployments: write
```

每项权限对应一个明确职责：

| 权限 | 在 CD 中的用途 |
|---|---|
| `contents: read` | checkout 部署脚本或读取仓库内容 |
| `actions: read` | 读取指定 CI 运行的信息并下载对应 Artifact |
| `deployments: write` | 创建或更新 GitHub Deployment 记录 |

CD 不需要 `contents: write`，因为它不应在部署过程中修改源代码、分支或标签。

CD 调用 [reusable-deploy.yml](../.github/workflows/reusable-deploy.yml) 时，调用方提供的 token 权限是上限。可复用工作流不能通过自身逻辑突破调用方或仓库策略授予更高权限；如果未来它增加 GitHub API 操作，应同步检查调用方的权限配置。

### 7.3 定时清理工作流

在 [scheduled-cleanup.yml](../.github/workflows/scheduled-cleanup.yml) 中，清理流程把“查询”和“删除”拆成两个 job：

计划 job：

```yaml
permissions:
	packages: read
```

执行 job：

```yaml
permissions:
	packages: write
```

这种拆分比整个工作流都使用 `packages: write` 更安全：

- 计划阶段只能列出 Package 版本，不能删除。
- 删除阶段才获得删除所需的写权限。
- 后续如果计划逻辑被修改或引入第三方 Action，影响范围更小。

## 8. `permissions`、Secrets、Variables 和 Environment 的区别

这几个概念经常一起出现，但职责不同：

| 概念 | 解决的问题 | 例子 |
|---|---|---|
| `permissions` | `GITHUB_TOKEN` 能调用哪些 GitHub API | `packages: write` |
| `secrets` | 如何安全保存敏感值 | `SLACK_WEBHOOK_URL`、云端私钥 |
| `vars` | 如何保存非敏感配置 | 部署 URL、环境名称 |
| `env` | 如何把值传给当前进程 | `GH_TOKEN`、`IMAGE_TAG` |
| `environment` | 如何保护部署目标并提供环境变量/Secrets | `staging`、`production` |
| PAT | 用个人或机器人身份访问 API | `secrets.RELEASE_TOKEN` |
| GitHub App | 使用应用身份并授予指定仓库权限 | 自动化发布机器人 |
| OIDC | 使用短期身份令牌登录云平台 | `id-token: write` |

一个 job 可以同时需要多种能力：

```yaml
jobs:
	production-deploy:
		environment: production
		permissions:
			contents: read
			deployments: write
			id-token: write
		steps:
			- uses: actions/checkout@v4
			- run: ./deploy.sh
```

这里：

- `permissions` 负责 GitHub API 和 OIDC token。
- `environment` 负责生产审批、生产 Secrets 和部署保护。
- `id-token: write` 仍需要配合云平台的信任策略。
- `contents: read` 只负责读取仓库代码。

## 9. 出现 403 或 `Resource not accessible by integration` 时如何排查

### 第一步：确认失败的具体操作

先判断失败的是哪一种操作：

- checkout 失败：通常检查 `contents: read`。
- 推送 GHCR 失败：检查 `packages: write`、镜像名称、Package 与仓库的关联关系。
- 下载其他工作流的 Artifact 失败：检查 `actions: read`、run ID 和 Artifact 名称。
- 创建 Deployment 失败：检查 `deployments: write`。
- 添加 Issue 评论失败：检查 `issues: write`。
- 添加 PR 标签失败：检查 `pull-requests: write`。
- 上传 CodeQL 结果失败：检查 `security-events: write`。
- 获取 OIDC token 失败：检查 `id-token: write` 以及云端信任配置。

### 第二步：检查权限作用域

按以下顺序查看：

1. 失败 step 所在的 job。
2. 该 job 是否有自己的 `permissions` 块。
3. 如果有，是否漏写了顶层原本提供的权限。
4. 工作流触发事件是否来自 Fork 或 Dependabot。
5. 仓库、组织或企业是否禁止写权限。
6. 是否实际上使用了 PAT、GitHub App token 或云端密钥，而不是 `GITHUB_TOKEN`。

### 第三步：查看 GitHub 运行日志

在 job 的初始化日志中查看 GitHub 显示的 `GITHUB_TOKEN Permissions` 信息。它可以帮助确认最终授予的是 `read`、`write` 还是 `none`。

不要把 token 本身输出到日志。调试时可以安全地输出非敏感信息，例如：

```yaml
- name: Show repository context
	run: |
		echo "repository=$GITHUB_REPOSITORY"
		echo "event=$GITHUB_EVENT_NAME"
		echo "sha=$GITHUB_SHA"
```

使用 GitHub CLI 时，通过环境变量传递 token：

```yaml
- name: Query repository metadata
	env:
		GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
	run: gh api "repos/${GITHUB_REPOSITORY}" --jq '.full_name'
```

### 第四步：查看 endpoint 的官方要求

GitHub API 某些 endpoint 的权限名称并不完全符合直觉。例如，Issue 和 Pull Request 在 API 模型中存在重叠。应当根据实际调用的 REST/GraphQL endpoint 或 Action 文档确定最小权限，而不是直接授予 `write-all`。

### 第五步：判断是否需要 GitHub App 或 PAT

如果所需能力不在 `GITHUB_TOKEN` 可用范围内，可以考虑：

- 创建权限范围更窄的 GitHub App，并在 workflow 中生成安装 token。
- 创建细粒度 PAT，保存为 Repository Secret 或 Environment Secret。

PAT 或 GitHub App token 的能力可能超出 `GITHUB_TOKEN`，因此必须：

- 使用最小仓库范围和最小 API 权限。
- 放到受保护的 Environment 中。
- 不在命令行参数、日志或 Artifact 中暴露。
- 定期轮换和审计。

## 10. 安全最佳实践

### 10.1 使用最小权限

推荐顺序：

1. 先设置 `permissions: {}` 或 `contents: read`。
2. 运行工作流，找出实际失败的 GitHub API 操作。
3. 只增加对应的一个权限范围。
4. 尽量把 `write` 放在独立 job。

不推荐：

```yaml
permissions: write-all
```

### 10.2 将不可信代码与写权限隔离

来自 PR 的代码可能修改构建脚本、测试脚本或依赖安装逻辑。不要让它与以下内容处于同一个高权限 job：

- 生产 Secrets。
- `packages: write`。
- `contents: write`。
- `deployments: write`。
- 云平台长期密钥。

更安全的结构是：

```text
pull_request
	└─ test: contents: read

push to main/tag
	├─ publish: contents: read + packages: write
	└─ deploy: contents: read + deployments: write + id-token: write
```

### 10.3 不要把权限和 Secret 混为一谈

即使某个 job 只有 `contents: read`，如果它可以读取一个高权限 PAT Secret，那么执行任意脚本的 Action 仍可能通过 PAT 进行高权限操作。因此需要同时控制：

- `GITHUB_TOKEN` 的 `permissions`。
- job 是否能访问 Secrets。
- 使用的第三方 Action 是否可信。
- 是否 checkout 或执行了不可信代码。
- self-hosted runner 是否可能残留数据。

### 10.4 固定第三方 Action 版本

生产工作流应优先使用经过审核的版本，必要时固定到完整 commit SHA：

```yaml
- uses: actions/checkout@<full-commit-sha>
```

使用 `@v4` 等主版本标签更方便，但需要信任 Action 维护者并配合 Dependabot 或定期审计。

### 10.5 OIDC 代替长期云密钥

云部署优先使用：

```yaml
permissions:
	id-token: write
```

然后在云端限制 token 的 subject、repository、ref 和 Environment。不要仅凭 `id-token: write` 就认为部署已经安全。

### 10.6 保护高风险 job

对于发布、删除和生产部署 job，建议同时使用：

- 分支或标签条件。
- `environment`。
- Required reviewers。
- 并发控制，避免多个发布同时进行。
- 独立的 job 级权限。
- 对输入和 Artifact 做格式校验。

### 10.7 不要使用权限绕过脚本安全问题

权限最小化不能替代脚本安全。使用来自 Issue、PR 标题、分支名或 Artifact 的值时：

- 不要直接拼接到 shell 代码中。
- 优先通过 `env` 传给脚本。
- 对 URL、镜像 tag、文件名和 JSON 做格式校验。
- 不要把不可信 Artifact 直接作为 shell 脚本执行。

## 11. GitLab CI/CD 对比

| GitHub Actions | GitLab 中较接近的概念 | 说明 |
|---|---|---|
| `GITHUB_TOKEN` | `CI_JOB_TOKEN` 的部分用途 | 都是工作流运行时 token，但权限模型和 API 范围不同 |
| `permissions.contents` | 仓库读写或 Job Token 对仓库 API 的访问 | GitHub 细分为 scope，不能简单一一对应 |
| `permissions.packages` | GitLab Container Registry 权限 | 控制 GitHub Packages/GHCR 的读写 |
| `permissions.actions` | GitLab Pipeline/Job API 访问 | 用于 Actions 工作流运行和相关 API |
| `permissions.deployments` | Deployments/Environment 相关 API | 只控制 GitHub Deployment 记录，不等于云平台部署权限 |
| `permissions.id-token` | GitLab OIDC/JWT 配置 | 都可以用于无长期密钥的云认证 |
| Repository Secret | CI/CD Variables | GitHub 还区分 Repository、Organization 和 Environment Secret |
| `upload-artifact` | Job artifacts | Actions Artifact 与 GHCR Package 是两类不同资源 |
| PAT/GitHub App | Project Access Token/Deploy Token/机器人账号 | 都是额外身份，应单独配置最小权限 |

GitLab 中常见的“整个项目共享一个 Job Token”思路，在 GitHub Actions 中不应直接照搬。GitHub 更推荐让每个 job 明确声明自己的 `permissions`。

## 12. 权限设计检查清单

提交工作流前，可以按以下清单检查：

- [ ] 是否在工作流顶层设置了 `permissions: contents: read` 或更严格的默认值？
- [ ] 是否避免了 `write-all`？
- [ ] 是否为每个需要写权限的 job 单独设置了 `permissions`？
- [ ] job 级权限中是否重新列出了该 job 需要的 `contents: read`？
- [ ] GHCR 发布是否只给发布 job `packages: write`？
- [ ] Package 删除是否与只读查询 job 分离？
- [ ] 跨工作流读取 Artifact 是否使用 `actions: read`，而不是 `actions: write`？
- [ ] Deployment 记录是否只在部署 job 使用 `deployments: write`？
- [ ] 云登录是否使用 OIDC，并配置了 `id-token: write` 和云端信任策略？
- [ ] Fork PR 和 Dependabot 是否不会接触写权限或生产 Secrets？
- [ ] 是否避免在 `pull_request_target` 或 `workflow_run` 中执行未经审核的代码？
- [ ] 是否审查了第三方 Action 的来源和版本？
- [ ] 是否没有在日志、Artifact 或命令行参数中打印 token/Secret？
- [ ] 403 错误是否根据具体 endpoint 的最小要求解决，而不是直接扩大权限？

## 13. 速查表

| 需求 | 推荐权限 |
|---|---|
| checkout 仓库 | `contents: read` |
| 只运行本地测试 | `permissions: {}` 或 `contents: read` |
| 发布 GHCR 镜像 | `contents: read` + `packages: write` |
| 读取其他 Actions 运行/Artifact | `contents: read` + `actions: read` |
| 取消或重新运行工作流 | 通常需要 `actions: write` |
| 创建 Deployment 记录 | `contents: read` + `deployments: write` |
| 添加 Issue 评论 | `issues: write` |
| 修改 Pull Request 标签 | `pull-requests: write` |
| 创建 Check run | `checks: write` |
| 创建 commit status | `statuses: write` |
| 上传 CodeQL 结果 | `security-events: write` |
| 读取 Dependabot alerts | `vulnerability-alerts: read` |
| 生成 Artifact attestation | `attestations: write`，通常还需要 `id-token: write` |
| 云平台 OIDC 登录 | `id-token: write`，通常还需要 `contents: read` |
| GitHub Pages 部署 | `pages: write`，通常还需要 `id-token: write` |
| 创建 Release 或推送代码 | `contents: write`，仅在确有需要时使用 |
