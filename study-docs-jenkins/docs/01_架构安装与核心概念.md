# 01. Jenkins 架构、安装与核心概念

## 1. Jenkins 的运行模型

Jenkins 是一个可扩展的自动化服务器。一次流水线执行可以抽象为：

```text
SCM/Webhook/定时器/手动操作
            ↓
      Job 与 Build 排队
            ↓
 Controller 分配 Executor
            ↓
 Agent 创建 Workspace 并执行 Step
            ↓
  日志、测试报告、制品、通知和审计
```

| 概念 | 含义 | 生产建议 |
|---|---|---|
| Controller | 保存配置、调度构建、提供 Web/API、运行插件 | 不承担普通构建，不给它分配构建 Executor |
| Agent/Node | 实际运行流水线的机器、容器或 Pod | 按工具链和信任边界分组，尽量短生命周期 |
| Executor | 一个 Node 可同时运行的执行槽位 | 数量按 CPU、内存、I/O 和外部系统容量压测 |
| Job | 可配置的任务定义 | 优先 Pipeline 或 Multibranch Pipeline |
| Build/Run | Job 的一次执行 | 用编号、提交 SHA 和制品 digest 关联 |
| Workspace | Agent 上的工作目录 | 不假设跨 Agent 永久存在，运行结束清理 |
| Plugin | 扩展 Jenkins 的能力 | 只安装必要且维护中的插件 |
| Queue | 等待可用 Executor 的队列 | 排查排队时间、标签不匹配和容量不足 |

Jenkins 核心不是“一个 YAML 解释器”。Jenkinsfile 是 Groovy DSL，流水线由 Pipeline 插件执行，Git、Docker、Kubernetes、报告和通知通常由插件提供步骤。

## 2. Job 类型和选择

- **Pipeline**：一个固定的流水线 Job，适合单仓库或集中入口。
- **Multibranch Pipeline**：按分支、标签和 Pull/Merge Request 自动发现并创建子 Job，适合仓库中的 Jenkinsfile。
- **Organization Folder**：扫描 GitHub/GitLab 组织或组下的多个仓库，自动创建 Multibranch Pipeline。
- **Freestyle Project**：历史任务或极简单的脚本仍可使用，但不适合作为新项目默认方案。
- **Folder**：隔离团队、权限、凭据域和命名空间。
- **Downstream Job**：通过 `build` 或触发器被上游调用，用于拆分生命周期或复用已有任务。

新项目通常使用 `Organization Folder → Multibranch Pipeline → Jenkinsfile`。把“发现仓库”和“执行流水线”分开，避免为每个分支手工创建 Job。

## 3. 安装与基线

### 3.1 Docker 试用

适合本地实验，不代表生产部署。生产环境需要持久卷、HTTPS、备份、固定插件版本、资源限制和外部 Agent。

```text
docker run --name jenkins-lab \
  --publish 8080:8080 --publish 50000:50000 \
  --volume jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts-jdk17
```

首次启动后读取初始管理员密码，完成向导。不要直接把 Controller 容器的 Docker socket 暴露给不可信 Pipeline。

### 3.2 Linux/Windows 服务

- Linux 使用发行版包、systemd 或官方 WAR；通过专用用户运行，JENKINS_HOME 使用独立磁盘。
- Windows 使用服务或 WAR，Agent 命令可使用 `bat`/PowerShell；服务账号只授予构建所需目录和工具权限。
- 生产部署优先采用受支持的容器或包管理方式，并记录 Jenkins、Java、插件和操作系统版本。

### 3.3 Java 和版本

Jenkins LTS、Java、插件必须组合在支持矩阵内。升级前检查：

1. Jenkins LTS 与 Java 版本是否匹配。
2. 所有插件是否有依赖冲突或已弃用。
3. Shared Library、Job DSL、JCasC 是否能在预生产启动。
4. 备份和回滚是否可用。
5. 一个真实流水线是否完成端到端验证。

## 4. Controller、Agent 和标签

Controller 的推荐配置是 `0` 个 Executor；构建节点通过标签分配：

```groovy
pipeline {
    agent { label 'linux-docker' }
    stages {
        stage('Inspect agent') {
            steps {
                sh 'whoami && uname -a && git --version && docker version'
            }
        }
    }
}
```

标签是能力和信任边界的声明，例如 `linux`, `docker`, `k8s`, `trusted-release`。不要仅用一个 `any` 标签让所有项目共享拥有生产凭据的 Agent。

Agent 方式包括：

- 静态 VM 或裸机：稳定但维护成本高。
- SSH/Inbound Agent：适合固定节点。
- Docker Agent：为流水线提供可复现工具链。
- Kubernetes 动态 Pod：按需创建，构建结束回收；见高级示例。
- 云厂商 Agent：需要审查实例权限、网络和成本。

## 5. Pipeline as Code

最小的声明式 Pipeline：

```groovy
pipeline {
    agent any
    stages {
        stage('Hello') {
            steps {
                echo "Job=${env.JOB_NAME}, Build=${env.BUILD_NUMBER}"
            }
        }
    }
    post {
        always {
            echo "result=${currentBuild.currentResult}"
        }
    }
}
```

推荐把它保存为仓库根目录的 `Jenkinsfile`。Jenkins Web UI 只保留 Job 指向的仓库、分支发现、凭据和 Agent 等平台配置。

## 6. 插件和扩展边界

安装插件前回答三个问题：

1. Jenkins 核心或现有插件是否已经提供该能力？
2. 插件是否仍维护、权限是否过大、依赖是否可接受？
3. 能否在预生产和回滚流程中验证？

插件供应链和 Pipeline 代码一样重要。生产 Controller 应固定插件清单，定期扫描安全公告，升级前保留备份。不要在流水线中动态安装插件。

## 7. 备份、恢复和升级

至少备份：

- `JENKINS_HOME` 中的 Job、凭据元数据、用户、插件配置和脚本批准记录。
- 插件清单、Jenkins/Java 版本、JCasC 文件和反向代理配置。
- 外部制品库、代码仓库、密钥管理系统和数据库的依赖信息。

备份不等于可恢复。应定期在隔离环境恢复一个 Controller，验证登录、Job 扫描、凭据引用、流水线、制品和通知。
