# 09. 安全、权限与软件供应链

## 1. Jenkins 安全边界

Jenkins 安全至少包含四个不同边界：

1. **用户/API 认证**：谁能登录 Jenkins、调用 API 或触发 Build。
2. **Jenkins 授权**：用户能看哪些 Folder/Job、配置/构建/取消/读取凭据。
3. **凭据授权**：某个 Job 是否能使用特定 Credential ID。
4. **Agent/云权限**：Pipeline 进程在操作系统、容器、Kubernetes 或云账号上能做什么。

Jenkins 的 Job 权限不等于 Shell 权限；`withCredentials` 绑定凭据也不等于云端自动授权。四层要分别最小化。

## 2. 认证和授权

认证方式：本地用户、LDAP/Active Directory、OIDC/SAML、反向代理和 GitHub/GitLab 身份。生产优先使用企业身份提供商、MFA、短会话和集中离职回收。

授权策略：

- Matrix Authorization：按用户/组授予全局、Item、Agent、凭据等权限。
- Role-based Authorization Strategy：按全局、项目、凭据角色分层，适合大型组织。
- Folder 权限：团队和环境的天然隔离边界。
- Item/Agent 权限：限制谁能配置、构建、取消 Job，谁能使用某类 Agent。

建议的团队角色：

| 角色 | 最小能力 |
|---|---|
| Developer | 查看、构建自己的 CI、读取非敏感日志和报告 |
| Reviewer | 查看 PR 检查、批准代码/环境，不直接读取 Secret |
| Release | 启动/批准生产发布，读取必要结果，不管理系统 |
| Platform Admin | 管理插件、节点、JCasC、凭据域和备份 |
| Auditor | 只读 Job、配置、审计和构建记录 |

不要给普通用户 `Overall/Administer`、`Credentials/View` 或 Script Approval。定期审查组成员、Folder ACL、Job Token 和失效用户。

## 3. Web 安全基线

- 全程 HTTPS，Jenkins URL、反向代理 Header 和 WebSocket/Agent 通道配置一致。
- 启用 CSRF 防护，不在脚本中关闭 Crumb Issuer；API 客户端使用 API Token。
- 禁止匿名读写和匿名 Build，Webhook 使用签名/Token/来源限制。
- 限制管理端口、JNLP/Inbound Agent 通道、脚本控制台和 CLI 的网络暴露。
- 配置安全响应头、登录失败限制、会话超时和审计日志。
- 备份前加密；不要把 `secrets.xml` 当作可直接分享的配置文件。

## 4. 凭据和 Secret 管理

Jenkins Credentials Store 只解决存储和注入，不解决业务授权。最佳实践：

- 凭据按 Folder、环境、Job 和用途拆分，ID 使用可审计命名。
- 凭据以短期 Token、角色联邦、OIDC、Managed Identity 为优先。
- Secret 只在最小 stage 的 `withCredentials` 闭包内可见。
- 定期轮换，记录使用者和最后使用时间，删除旧凭据并验证回滚。
- Secret 不得出现在参数、Jenkinsfile、共享库日志、构建描述、制品、缓存、Docker layer 或错误通知。
- 对 Secret file 使用临时路径，保证工作区不会被归档或残留。

Jenkins 会尝试对已知 Secret 做日志遮蔽，但以下方式仍可能泄露：Shell 调试、编码/截断、进程列表、恶意脚本、异常归档和外部服务。因此“日志遮蔽”不是安全边界。

## 5. Script Approval 和 Groovy Sandbox

Jenkins Pipeline 的 Groovy Sandbox 阻止部分危险 API。管理员在 In-process Script Approval 中批准的签名会扩大能力范围：

- 优先改写代码使用受支持的 Pipeline Step，不要批准任意 `methodMissing`、反射、文件系统和 Jenkins 内部 API。
- 审批记录纳入变更审计，说明风险和使用 Job。
- 可信 Shared Library 单独维护、严格评审；不可信项目不要让 Jenkinsfile 直接调用管理 API。
- 禁止在 Jenkinsfile 中使用脚本控制台式的任意系统操作。

## 6. 不可信代码与 Agent 隔离

PR、Fork、外部贡献和依赖构建都可能执行恶意代码。隔离策略：

- PR CI 使用无生产凭据的短生命周期 Agent。
- 可信发布 Job 不直接执行 PR 分支中的 Jenkinsfile；发布逻辑来自受保护分支/固定共享库。
- 将 Docker socket、宿主机目录、云元数据服务和 Kubernetes ServiceAccount 从不可信 Agent 中移除。
- 为构建用户、容器和 Pod 设置非 root、资源限制、网络策略和只读文件系统。
- 将构建、扫描、签名、发布拆为不同权限的 Job/Agent。

## 7. 插件供应链

插件拥有运行在 Jenkins Controller 上的代码能力。管理插件时：

1. 使用官方 Update Center/受信来源。
2. 固定版本和依赖，保存插件清单。
3. 关注安全公告、维护状态和最近发布。
4. 在隔离 Controller 升级，运行代表性 Pipeline。
5. 删除未使用插件，减少攻击面。
6. 禁止 Pipeline 运行时下载并安装插件。

## 8. 构建供应链

推荐的安全链路：

```text
受保护 SCM
   ↓
可信 Jenkinsfile/Shared Library
   ↓
隔离 Agent + 依赖锁定
   ↓
测试、SAST、SCA、Secret Scan
   ↓
构建不可变制品 + SBOM
   ↓
漏洞门禁 + provenance/签名
   ↓
受保护环境审批
   ↓
按 digest 发布 + 运行时验证
```

工具可以使用 SonarQube、OWASP Dependency-Check、Trivy、Grype、Syft、Cosign、SLSA/attestation 服务等。工具输出只是证据，门禁阈值、漏洞例外、到期时间和责任人必须版本化并审计。

## 9. OIDC 与云联邦

OIDC/Workload Identity 的核心是：Jenkins 或其 Agent 获取短期身份 Token，云端根据 issuer、subject、audience 和 Job/Folder/环境条件换取角色。必须同时配置：

- Jenkins 身份提供者和 Token 签发策略。
- 云端 Federated Credential/Trust Policy。
- 最小云 RBAC/IAM 角色。
- 仅对可信 Job/分支/标签/环境授予身份。
- Token audience、过期时间和审计日志。

`id-token: write` 这类 GitHub 概念在 Jenkins 中没有单个统一开关，通常由插件、云身份或 Agent 平台实现。不要把一个长期云 Secret 粗暴地复制到 Jenkins 全局凭据。

## 10. 审计和合规

需要记录：登录、权限变化、凭据创建/使用、Job 配置变化、脚本审批、插件升级、生产发布、人工审批、失败和取消。使用 Audit Trail、支持的日志转发和外部 SIEM；日志本身做访问控制和保留策略。

合规报告应包含：代码 SHA、Jenkins Build URL、构建器身份、依赖锁文件、工具版本、扫描结果、制品 digest、审批者和部署目标。不要用一份“成功日志”替代完整 provenance。

## 11. 安全检查清单

- [ ] Jenkins URL 使用 HTTPS，匿名和 CSRF 基线正确。
- [ ] Controller 无普通构建 Executor，Agent 按信任边界隔离。
- [ ] Folder/RBAC/凭据使用权限定期审计。
- [ ] Fork PR 不可读取生产 Secrets 或云身份。
- [ ] Shared Library、插件和 Jenkinsfile 有版本和评审。
- [ ] 构建输出包含 SBOM、扫描结果、digest 和签名/证明。
- [ ] 生产发布有环境审批、并发锁、回滚和审计记录。
