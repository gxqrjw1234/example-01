# 05. 控制流、并发与错误处理

## 1. `when` 条件

`when` 决定一个 stage 是否进入执行。它类似 GitHub Actions 的 job/step `if`，但 Jenkins Build 通常已经被触发：

```groovy
stage('Deploy') {
    when {
        allOf {
            branch 'main'
            not { changeRequest() }
            expression { return params.ENVIRONMENT == 'staging' }
        }
    }
    steps {
        sh './scripts/deploy.sh staging'
    }
}
```

常用条件：

- `branch 'main'`、`buildingTag()`、`tag 'v*'`。
- `changeRequest()`、`changeRequest(target: 'main')`。
- `environment name: 'DEPLOY_ENV', value: 'prod'`。
- `triggeredBy 'TimerTrigger'` 或具体触发器类。
- `expression { ... }`：最后手段，逻辑要短并且返回布尔值。
- 组合 `allOf`、`anyOf`、`not`。

`beforeAgent true` 可以在分配昂贵 Agent 之前先评估条件：

```groovy
stage('Production') {
    when {
        beforeAgent true
        allOf {
            branch 'main'
            buildingTag()
        }
    }
    agent { label 'trusted-release' }
    steps { echo 'release' }
}
```

## 2. `post` 与状态

`post` 支持 `always`、`success`、`failure`、`unstable`、`aborted`、`unsuccessful`、`changed` 和 `cleanup`。报告通常使用 `always`，资源清理使用 `cleanup`：

```groovy
post {
    always {
        junit testResults: 'reports/**/*.xml', allowEmptyResults: true
    }
    failure {
        echo "failed: ${env.BUILD_URL}"
    }
    cleanup {
        deleteDir()
    }
}
```

注意：`currentBuild.result` 可能为 `null`，表示尚未显式设置结果；`currentBuild.currentResult` 通常返回当前结果字符串。不要把“跳过 stage”误判成“测试成功”，应在摘要中区分 `SUCCESS`、`UNSTABLE`、`FAILURE`、`ABORTED`。

## 3. 异常和显式失败

```groovy
script {
    try {
        sh './scripts/risky-step.sh'
    } catch (err) {
        currentBuild.result = 'FAILURE'
        echo "step failed: ${err.class.simpleName}"
        throw err
    }
}
```

- `error('message')` 立即终止当前流程并失败。
- `unstable('message')` 将结果设为不稳定，适合非阻断质量问题。
- `catchError` 可以设置构建结果和阶段结果：

```groovy
catchError(
    buildResult: 'UNSTABLE',
    stageResult: 'FAILURE',
    message: 'lint failed; continue for report'
) {
    sh './scripts/lint.sh'
}
```

不要为了“让流水线变绿”到处使用 `|| true` 或 `continue-on-error`。允许失败必须有业务理由、可观测的警告和最终门槛。

## 4. 重试、超时和取消

```groovy
timeout(time: 10, unit: 'MINUTES') {
    retry(2) {
        sh './scripts/test-against-service.sh'
    }
}
```

- `timeout` 防止网络、外部系统或进程挂死。
- `retry` 只适合幂等、暂时性错误；不要重试数据迁移、扣款、生产发布等非幂等操作。
- 重试前最好区分连接失败和代码失败，限制次数并记录第几次尝试。
- 用 `disableConcurrentBuilds` 或 Lockable Resources 避免同一环境被并发修改。

## 5. 并行执行

声明式 Pipeline：

```groovy
stage('Verification') {
    parallel {
        stage('Unit') {
            steps { sh './scripts/unit.sh' }
        }
        stage('Lint') {
            steps { sh './scripts/lint.sh' }
        }
        stage('Integration') {
            steps { sh './scripts/integration.sh' }
        }
    }
}
```

动态并行通常需要 `script`：

```groovy
script {
    def branches = [:]
    ['linux', 'windows'].each { os ->
        branches[os] = {
            if (os == 'windows') {
                bat 'run-tests.bat'
            } else {
                sh './run-tests.sh'
            }
        }
    }
    parallel branches
}
```

注意动态闭包的变量捕获，使用 `def currentOs = os` 避免循环变量被所有分支共享。并行分支要使用独立工作目录或 `ws("${env.WORKSPACE}@${currentOs}")`，避免同时写同一个文件。

`parallelsAlwaysFailFast()` 适合单个失败后其余分支没有继续价值的测试。若每个分支都必须产出报告，使用 `catchError` 让其他分支完成，再在汇总阶段统一判断。

## 6. Lock、Throttle 和并发组

部署共享环境时使用 Lockable Resources：

```groovy
lock(resource: 'staging-environment') {
    timeout(time: 20, unit: 'MINUTES') {
        sh './scripts/deploy.sh staging'
        sh './scripts/smoke-test.sh staging'
    }
}
```

锁的范围应尽可能小。不要把整个 CI 包进生产锁。需要按资源名动态锁时，先对白名单后的环境名做映射，不要让用户任意构造资源名访问不应有的资源。

Throttle Concurrent Builds 插件可以按 Job、类别、节点或参数限制并发。它和 `disableConcurrentBuilds` 解决的问题不同：前者是跨 Job/类别的容量控制，后者是单 Job 的串行策略。

## 7. 输入审批

```groovy
stage('Approve production') {
    when { branch 'main' }
    steps {
        timeout(time: 30, unit: 'MINUTES') {
            input(
                message: '确认部署到生产环境？',
                ok: 'Deploy',
                submitter: 'release-team'
            )
        }
    }
}
```

`input` 是暂停等待；它不替代 Jenkins 全局/Folder/Job 权限、代码评审或生产环境策略。审批前应显示版本、提交 SHA、测试摘要和目标环境，避免审批人只能看到一句模糊提示。

## 8. 下游调用和结果

`build` Step：

```groovy
def child = build(
    job: 'publish-metadata',
    parameters: [string(name: 'IMAGE_TAG', value: env.IMAGE_TAG)],
    wait: true,
    propagate: false
)
if (child.result != 'SUCCESS') {
    error "publish-metadata failed: ${child.result}"
}
```

- `wait: true` 等待下游完成；`false` 只负责触发。
- `propagate: true` 会把下游失败传播到当前 Pipeline；复杂编排可用 `false` 后显式处理。
- 跨 Job 文件使用 `copyArtifacts` 插件或外部制品库，字符串用参数/归档元数据，不要依赖另一 Job 的工作区。

## 9. 对应 GitHub Actions 状态函数

| GitHub Actions | Jenkins 近似实现 |
|---|---|
| `success()` | 默认 stage/post 条件或 `currentBuild.currentResult == 'SUCCESS'` |
| `failure()` | `post { failure { ... } }`、`catchError` 后判断 |
| `always()` | `post { always { ... } }` |
| `cancelled()` | `post { aborted { ... } }` |
| `needs.job.result` | `build(..., propagate: false).result` 或显式编排变量 |
| `continue-on-error` | `catchError`、`unstable`，但需要明确最终门槛 |
