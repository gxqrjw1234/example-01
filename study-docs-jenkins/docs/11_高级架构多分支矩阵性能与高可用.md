# 11. 高级架构：多分支、矩阵、性能与高可用

## 1. Multibranch Pipeline

Multibranch Pipeline 根据 SCM 分支、标签和 PR 自动发现子 Job，并为每个分支读取对应版本的 Jenkinsfile。适合：

- 分支级 CI 和 PR 检查。
- release 分支和标签发布。
- 统一仓库模板与团队自定义配置。

设计要点：

- 配置扫描间隔和 Webhook，避免高频全量扫描。
- 限制分支发现、PR 策略和历史保留，避免 Job 数量无限增长。
- Jenkinsfile 来自分支意味着 PR 代码可影响执行逻辑，必须配置信任策略和隔离 Agent。
- 关键发布逻辑来自受保护分支或固定 Shared Library，而不是任意 PR 修改。
- 通过 `BRANCH_NAME`、`CHANGE_ID`、`TAG_NAME` 做条件，但不要把未验证的分支名直接作为 Kubernetes namespace、镜像标签或云资源名。

## 2. Organization Folder

Organization Folder 扫描 GitHub Organization 或 GitLab Group，自动创建 Multibranch Pipeline。企业实践：

- 用 Folder 继承权限、凭据域、Agent 选择和公共库。
- 用仓库命名/Topic/文件存在性控制发现范围。
- 对组织级凭据和 GitHub App 权限进行最小化。
- 设定 orphaned item 策略清理已删除仓库/分支的 Job。
- 扫描和 Webhook 使用 API 限流退避。

## 3. Declarative Matrix

Jenkins Declarative Pipeline 支持矩阵轴：

```groovy
pipeline {
    agent none
    stages {
        stage('Test matrix') {
            matrix {
                axes {
                    axis {
                        name 'JDK'
                        values '17', '21'
                    }
                    axis {
                        name 'OS'
                        values 'linux', 'windows'
                    }
                }
                excludes {
                    exclude {
                        axis { name 'OS'; values 'windows' }
                        axis { name 'JDK'; values '17' }
                    }
                }
                stages {
                    stage('Run') {
                        agent { label "${OS}" }
                        steps {
                            echo "JDK=${JDK}, OS=${OS}"
                            script {
                                if (OS == 'windows') {
                                    bat "run-tests-${JDK}.bat"
                                } else {
                                    sh "./run-tests-${JDK}.sh"
                                }
                            }
                        }
                    }
                }
            }
        }
    }
}
```

矩阵会产生大量 Executor、Agent、报告和制品。使用 `failFast`/`parallelsAlwaysFailFast`、并发上限、合理轴组合和结果聚合控制成本。矩阵变量来自配置，不能直接信任为 Shell 片段。

## 4. 动态并行与资源容量

矩阵适合静态、可审查的组合；动态并行适合从配置文件读取测试分片。两者都要考虑：

- Agent 并发是否足够，是否会让 Queue 爆炸。
- 外部数据库、Registry、云 API 是否支持并发。
- 结果文件是否使用唯一名称，避免覆盖。
- 失败分支是否仍上传报告。
- 重试是否造成外部副作用。

Jenkins 的“并行”不是免费资源；要用 Throttle、节点标签、Kubernetes request/limit 和外部系统配额共同控制。

## 5. 性能优化

### Controller

- 禁止构建在 Controller 执行，减少插件和 Job 配置数量。
- 升级 JVM、Pipeline durability 和日志策略前做基准。
- 减少高频 SCM 轮询、全量组织扫描和巨型控制台日志。
- 将大型 Artifact、日志和缓存外置。
- 避免在 Groovy 中加载大文件、构造巨大对象或使用复杂 CPS 循环。

### Pipeline

- 使用轻量、预构建的 Agent 镜像，减少每次安装依赖。
- 依赖使用锁文件和可控缓存；缓存键按工具/平台/依赖变化。
- 尽早运行廉价 lint，独立并行慢测试。
- 只在需要的阶段分配昂贵 Agent，必要时 `beforeAgent true`。
- 构建一次、发布多次，不在每个环境重新构建。
- 用 `skipDefaultCheckout(true)` 避免重复 checkout。

### SCM

- 浅克隆只在不需要历史/标签时使用。
- 限制分支和 PR 发现范围，配置 orphaned item 清理。
- Webhook 优先于频繁轮询，使用增量扫描。

## 6. 高可用与灾备边界

传统 Jenkins Controller 不是无状态集群：多个 Controller 不能简单共享同一个 JENKINS_HOME。常见企业架构是：

```text
反向代理/身份层
        ↓
Jenkins Controller（单活 + 快速恢复）
        ↓
动态/静态 Agent
        ↓
外部 SCM、Artifact、Secret、日志、监控
```

高可用重点：

- JENKINS_HOME 使用可靠持久存储和快照；验证文件锁、性能和一致性。
- 热备或冷备 Controller 不共享活动工作目录，故障切换要有明确流程。
- Job/Pipeline/Shared Library/JCasC 在 SCM，外部化制品和 Secrets。
- 使用安全备份和恢复演练，而不是只追求“多副本”。
- 识别正在运行 Build 的恢复语义：重启、重放、重试和重新部署不一定幂等。
- 通过 CloudBees 等发行版或官方支持方案获得更强的企业能力时，仍要验证组件和许可边界。

## 7. Jenkins Configuration as Code

JCasC 管理 Controller 配置，例如安全域、授权、系统设置、工具和插件集成。它不等于完全管理所有 Job/凭据 Secret：

- 使用环境变量或外部 Secret 引用注入敏感值。
- 配置文件版本化、审查、lint 和分环境覆盖。
- 启动时检测未知配置，避免拼写错误静默失效。
- Job DSL/Organization Folder 管理 Job 结构，Shared Library 管理执行逻辑。
- 配置和插件版本成套测试。

本目录的 [06_jcasc-baseline.yaml](../examples/advanced/06_jcasc-baseline.yaml) 是学习基线，不能原样作为生产安全配置。

## 8. 重启、Replay 与失败恢复

- Pipeline `disableResume()` 只有在明确接受重启丢失时才使用。
- `preserveStashes` 允许有限次数的重启后恢复，但制品仍应外部持久化。
- Replay 用于诊断，不应成为生产修改 Pipeline 的正式路径。
- 重试发布前确认幂等性和外部状态；优先按 digest 重新部署。
- 将数据库迁移、DNS、证书和资源创建设计为可观测、可回滚或可补偿。

## 9. 企业模式

- 平台团队维护 LTS、插件目录、JCasC、Shared Library、Agent 镜像和安全基线。
- 应用团队维护仓库 Jenkinsfile、测试和服务部署配置。
- 通过 Folder、RBAC、凭据域和 Agent 标签隔离租户。
- 用模板提供默认安全选项，但允许项目在受控范围内扩展。
- 以 DORA 指标、Queue、失败原因、成本和安全事件驱动持续改进。
