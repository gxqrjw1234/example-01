# 04. 变量、参数、凭据与运行上下文

## 1. Jenkins 中的变量来源

| 来源 | 示例 | 作用域/特点 |
|---|---|---|
| Pipeline `environment` | `APP_ENV = 'ci'` | Pipeline 或 stage 作用域，值通常是字符串 |
| `withEnv` | `withEnv(['MODE=test'])` | 一个闭包内临时覆盖 |
| 构建参数 | `params.TARGET_ENV` | 用户/API 输入，必须校验 |
| Jenkins 内置环境变量 | `BUILD_NUMBER`、`JOB_NAME` | Build 和 Agent 运行时提供 |
| Multibranch 变量 | `BRANCH_NAME`、`CHANGE_ID`、`TAG_NAME` | 由 Branch Source 注入，项目相关 |
| `currentBuild` | `currentBuild.result` | Pipeline 当前运行对象，不能当普通字符串环境变量 |
| SCM 变量 | `GIT_COMMIT`、`GIT_BRANCH` | checkout/SCM 插件提供，需确认具体插件行为 |
| 凭据绑定 | `withCredentials` | 临时注入 Secret，离开闭包后失效 |
| Shared Library | `@Library`、全局变量 | 受版本和信任策略控制 |

## 2. 常用内置变量

常见变量包括：

- `BUILD_NUMBER`：当前 Job 的构建编号。
- `BUILD_ID`、`BUILD_TAG`：构建标识。
- `JOB_NAME`、`JOB_BASE_NAME`、`BUILD_URL`：Job 和页面信息。
- `WORKSPACE`：当前 Agent 工作目录；多 Executor/容器场景不要假设固定路径。
- `NODE_NAME`、`EXECUTOR_NUMBER`：Agent 和 Executor 信息。
- `JENKINS_URL`、`JOB_URL`：Jenkins 地址和 Job 地址。
- `BRANCH_NAME`、`TAG_NAME`：Multibranch 分支/标签。
- `CHANGE_ID`、`CHANGE_TARGET`、`CHANGE_BRANCH`：PR/MR 元数据。
- `GIT_COMMIT`、`GIT_PREVIOUS_COMMIT`：SCM 提交信息，是否完整取决于 checkout。

调试时可以打印非敏感字段：

```groovy
sh 'printf "job=%s build=%s branch=%s commit=%s\\n" "$JOB_NAME" "$BUILD_NUMBER" "$BRANCH_NAME" "$GIT_COMMIT"'
```

不要使用 `printenv` 作为生产调试习惯，因为环境中可能存在 Secret 或临时 Token。

## 3. 环境变量作用域

```groovy
pipeline {
    agent any
    environment {
        GLOBAL_MODE = 'ci'
    }
    stages {
        stage('One') {
            environment {
                STAGE_MODE = 'test'
            }
            steps {
                withEnv(['STEP_MODE=lint']) {
                    sh 'echo "$GLOBAL_MODE $STAGE_MODE $STEP_MODE"'
                }
            }
        }
    }
}
```

优先级和覆盖关系要保持简单：Pipeline 级定义稳定默认值，stage 级定义边界配置，动态值用 `withEnv`，不要在多个位置反复修改同一个 `env` 键。

`env.NAME = value` 可以在 `script` 中设置后续阶段可见的值，但它是字符串、可变全局状态，容易造成并发和可读性问题。更好的做法是使用函数返回值、文件、stash 或显式参数传递。

## 4. 构建参数

```groovy
parameters {
    choice(name: 'ENVIRONMENT', choices: ['dev', 'staging', 'prod'], description: '目标环境')
    booleanParam(name: 'RUN_E2E', defaultValue: false, description: '是否执行 E2E')
    string(name: 'IMAGE_TAG', defaultValue: '', description: '可选的不可变镜像标签')
}
```

使用时：

```groovy
script {
    if (!(params.ENVIRONMENT in ['dev', 'staging', 'prod'])) {
        error 'Unsupported environment'
    }
    if (params.IMAGE_TAG ==~ /.*[\\s;|&`$].*/) {
        error 'IMAGE_TAG contains unsafe characters'
    }
}
```

参数可以来自 UI、CLI、REST API、上游 `build` Step 或重放操作。所有外部值都要经过白名单、格式和长度校验。不要直接把参数拼入 `sh "..."`。

## 5. Credentials Store

常用凭据类型：

- Secret text：API Token、Webhook URL、短期访问令牌。
- Username with password：Registry、基础认证。
- SSH Username with private key：Git/SSH 或远程主机。
- Secret file：Kubeconfig、证书、配置文件；使用后删除。
- Certificate：TLS 客户端证书。
- Cloud-specific credentials：由云插件管理的短期或角色凭据。

凭据可以放在 System、Global 或 Folder/域中。Folder 凭据适合按团队和环境隔离。Job 只能使用被授权的凭据 ID；不要把 Secret 作为 Pipeline 参数或提交到仓库。

### 推荐绑定方式

```groovy
withCredentials([
    usernamePassword(
        credentialsId: 'registry-push',
        usernameVariable: 'REGISTRY_USER',
        passwordVariable: 'REGISTRY_PASSWORD'
    )
]) {
    sh '''
        set +x
        printf '%s' "$REGISTRY_PASSWORD" | docker login registry.example.com \
          --username "$REGISTRY_USER" --password-stdin
    '''
}
```

在 Shell 中使用单引号 Groovy 多行字符串，让 Secret 由 Shell 环境变量读取，而不是被 Groovy 预先插值。Jenkins 会尽力遮蔽日志中的 Secret，但遮蔽不是加密边界；恶意脚本仍可能读取进程环境、文件或网络。

### 文件凭据

```groovy
withCredentials([file(credentialsId: 'kubeconfig-staging', variable: 'KUBECONFIG')]) {
    sh 'kubectl --kubeconfig "$KUBECONFIG" get namespace'
}
```

不要把 Secret file 放进工作区后再归档；使用临时目录、限制权限并在 `post { cleanup { ... } }` 删除。

## 6. `currentBuild` 和运行上下文

```groovy
script {
    echo "number=${currentBuild.number}"
    echo "result=${currentBuild.currentResult}"
    echo "previous=${currentBuild.previousBuild?.number ?: 'none'}"
    currentBuild.displayName = "#${env.BUILD_NUMBER} ${env.BRANCH_NAME ?: 'unknown'}"
}
```

常用属性：`number`、`result`、`currentResult`、`displayName`、`description`、`duration`、`durationString`、`previousBuild`、`absoluteUrl`。不要在 Pipeline 中随意使用 `currentBuild.rawBuild` 读取内部对象；这可能触发脚本审批并破坏可移植性。

## 7. GitHub Actions Context 的 Jenkins 对照

| GitHub Actions | Jenkins 近似来源 |
|---|---|
| `github.sha` | `GIT_COMMIT` |
| `github.ref_name` | `BRANCH_NAME`、`TAG_NAME` 或 `GIT_BRANCH` |
| `github.repository` | SCM 配置、`GIT_URL` 或 Job 属性 |
| `github.actor` | `BUILD_USER_ID`（需 Build User Vars 插件）或 SCM 元数据 |
| `github.run_number` | `BUILD_NUMBER` |
| `github.run_id` | Jenkins Build URL/Job + Build Number |
| `runner.os` | `isUnix()`、`NODE_NAME` 或 Agent 标签 |
| `matrix.*` | Declarative `matrix` 的轴环境变量 |
| `secrets.*` | Credentials Store + `withCredentials` |
| `needs.*.outputs` | 同一 Pipeline 的变量/文件，或下游 Job 的参数和归档产物 |

Jenkins 没有一个统一的 `github` Context。运行上下文分布在环境变量、参数、`currentBuild`、SCM 插件和 Job API 中，因此要通过显式接口传递数据。

## 8. Secrets 安全清单

- [ ] 不在 `echo`、`archiveArtifacts`、JUnit XML、构建描述或通知正文中输出 Secret。
- [ ] 不使用 Groovy 双引号插值拼接 `credentials()` 值。
- [ ] 不把 Secret 写入 `stash`、Docker layer、镜像标签或缓存。
- [ ] PR/Fork 构建使用不含生产凭据的 Agent 和凭据集合。
- [ ] 云平台优先使用短期身份/OIDC 或 Workload Identity，避免长期密钥。
- [ ] 凭据按 Folder、环境和 Job 最小授权，并设置轮换和审计。
